# 小满童装：选款知识库 + 线索中台

**方案说明 · v1.0 · 2026-11**

> 把「幼儿园演出要穿什么 / 90 码还是 110 码」翻译成**款式 + 尺码 + 报价 + 资料包**；把「评论、私信、询盘」接住并分清谁是终端。
> 交付物是一个零安装、可离线运行的 Web 应用，外加一份标准 JSON 数据快照、一份 SQLite 库和一套 Excel 导入模板。

## 2. 四层架构

```
┌──────────────────────────────────────────────────────────────┐
│ 获客层   热门视频雷达（7 语种）→ 脚本生成 → 挂款号 → 私信话术   │
├──────────────────────────────────────────────────────────────┤
│ 交付层   报价单 · 款图数据页 · 质检摘要 · 大货确认页 · ZIP      │
├──────────────────────────────────────────────────────────────┤
│ 匹配层   归一化 → 款号精确/包含/模糊 → 系列别名 → 尺码段矩阵    │
│          → 置信度打分 → 消歧问题 → 候选集（可解释）             │
├──────────────────────────────────────────────────────────────┤
│ 数据层   SKU 272 · 编号 613 · 系列 26 · 尺码段 14 · 适穿 44     │
│          质检 12 · 面料 6 · 客户 8 · 线索 8 · 画像 17 · 选题 12 │
└──────────────────────────────────────────────────────────────┘
```

童装生意的六件事落在四层里，各归各位：

| 要做的事 | 落在哪层 | 具体是什么 |
|---|---|---|
| 选款 | 匹配层 + 获客层 | 场景 / 品类 / 系列 / 尺码 → 候选款；内容侧按市场反向推款 |
| 尺码 | 数据层 + 匹配层 | 14 个尺码段、44 条适穿关系、消歧问题；`4T` 只做搜索别名，报价前按实测身高体重核 |
| 面料 | 数据层 | 6 种面料，带克重区间、洗护、价格系数、起球与色牢度提示 |
| 质检 | 数据层 + 交付层 | 12 份报告按款挂载，资料包里出摘要，客户问得出就答得上 |
| 报价 | 交付层 | 阶梯价 + 面料系数 + 等级系数 + 运费估算，一页报价单 |
| 资料包 | 交付层 | 封面 + 报价 + 每款一页 + 质检 + 确认页，PDF / ZIP 两条出口 |

四层都可以单独替换：数据层换成 ERP 商品表同步、匹配层接大模型、交付层换公司模板、获客层接平台 API，界面不用动。

## 3. 三个关键设计决策

### 3.1 不做「唯一答案」，做「候选集 + 消歧问题 + 置信度」

这是整个方案最核心的一条。以一句真实的询盘为例：「幼儿园演出，女孩，大概 105cm。」

```
「幼儿园演出」 → 场景：演出 / 礼服
              → 品类候选：连衣裙（云朵泡泡 / 小满花园 / 海盐苏打）、纱裙两件套
「105cm」     → 尺码段候选：100（95–105cm）/ 110（105–115cm）
              → 推荐 110：演出按净身高、宁短不长，110 是这一档最稳的
```

所以系统给出的是：

1. **一张尺码段对应表**（销售照着念就行）；
2. **2–3 个值得跟进的候选款**（接口最多列 8 个），每个都带证据链（命中系列 / 命中尺码段 / 命中款号 / 文本相似）；
3. **一句能直接问出口的话**：「孩子净身高多少？水洗标上是 110 还是 4T？两个码表的实际尺寸差 2cm。」

置信度是显式打分的，不是黑箱：

```
编号精确命中（条码 EAN）        → 98
编号精确 / 包含命中（其他编号）  → 96
款式系列命中                    → 70 + 适穿置信度（已确认 +14 / 高 +10 / 中 +4 / 低 −6）
                                  + 版型一致 6（不一致 −8）；尺码段同时命中再 +14
尺码段命中                      → 62 + 适穿置信度（+ 版型一致 6）
名称 / 描述包含                 → 55
关键词命中                      → 42
同一款命中多条证据时取最高分，理由全部保留（不累加）
```

对外话术据此分级：**≥90 可直接报价 / ≥75 高置信可报但注明「以水洗标为准」/ ≥58 必须先消歧**。

注意一个现实：当前 44 条适穿关系里 **0 条「已确认」**（高 20 / 中 17 / 低 7）。所以不靠编号、只靠「系列 + 码段」的路径，最高只能到 86 分（70 + 高 10 + 版型一致 6），永远进不了「直接报价」档——这不是 bug，是提醒你：**版房复核没补完，系统就不许你把猜测当结论卖出去。**

### 3.2 编号归一：款号是主键，编号是外键

同一个款在不同客户、不同平台、不同年份有完全不同的叫法：`DR2601001`、`6972026112300`、`LC-2600B`、`云朵裙`、客户自己的 `TS-110-A`。

数据层把「款号」和「编号」拆成两张表：

```
products (272)                    codes (613)
  id  ───────────────┐              id
  sku  XM-DR-2601    └───────────  pid → products.id
  code DR2601001                  code  DR2601001 / 6972026… / LC-2600B
  nameZh 云朵泡泡…                 norm  去空格、大写、去符号
  dim  90–140cm                   type  款号 / 内部款号 / 条码 EAN / 客户款号 / 旧款号 / 竞品款号 / 平台款号
  material MD                     conf  高 / 中 / 低
  holes 170（克重）                source 款式开发表 / 客户订单 / 平台后台
  price 13.56
```

613 条编号的构成：款号 119、内部款号 119、条码 EAN 119、客户款号 119、旧款号 84、竞品款号 53。检索时先归一化再匹配：精确 → 包含（长编号优先）→ 编辑距离 ≤1（仅长度 ≥5 的数字码，防误伤）。这样客户发来一个裸编号，命中率远高于「按名称搜」。

### 3.3 「发资料」不是翻文件夹，是生成

销售真正的耗时不在报价，在**凑资料**：找款图、找尺码表、找检测报告、拼 PDF、改客户名。

系统把这件事变成一次生成：封面（客户名 + 资料编号 + 款号清单 + 免责说明）→ 报价单（条款 + 阶梯价 + 运费 + 有效期）→ 每个款一页数据页（款图、款号、编号对照、尺码段、面料克重、适穿关系、质检摘要、装箱参数）→ 大货前确认页（把「同系列不同码段」的风险前置到发货前）。

输出两条路径：

- **打印 → 另存为 PDF**：带款图，适合邮件正式报价；
- **ZIP 包**：README + 报价单.html + 产品数据页.html + 3 张 CSV + `img/`，体积小，适合 WhatsApp / 微信直接发。

### 3.4 数据要能自我纠错

每条适穿关系都有 `置信度 + 来源 + 消歧问题`。销售在「尺码适配图谱」里新增的关系不会直接生效，而是进入**待复核队列**；版房确认后才变「已确认」，下次匹配的置信度自动提高（+14）。

这条闭环决定了这个库三个月后是「越用越准」还是「越用越乱」。童装的码表还会随版型、面料缩水率变，不复核就会一路错下去。

## 4. 四个模块的具体实现

### 4.1 数据库：款号、编号、尺码段整合在一套主数据里

产品主表 20 多个字段，其中与「认款、认码」直接相关的：

| 字段 | 说明 | 当前覆盖 |
|---|---|---|
| `sku` / `code` | SKU 与主款号（唯一），如 `XM-DR-2601` / `DR2601001` | 272 |
| `nameZh` / `nameEn` | 中文名 `系列 款型｜颜色图案`；英文名给外单用 | 272 / 272 |
| `cat` / `brand` | 8 个品类 / 5 条品牌线（XIAOMAN、BABY、MINI、SPORT、OEM） | 272 |
| `dim` / `holes` | 尺码段（如 90–140cm）与克重（g/m²，现场最快判据） | 272 / 272 |
| `pos` | 版型：宽松 / 标准 / 修身，直接影响「要不要上浮一码」 | 272 |
| `material` | 6 种面料，带克重区间、洗护、价格系数 | 100% |
| `price` / `moq` / `pack` | 参考价（$3.47–46.05）、起订量（50–200 件）、装箱（件/袋、袋/箱、毛重、CBM） | 272 |
| `hs` | 按品类的出口税则号（6104.42 / 6110.20 / 6109.10 / 6201.40 / 6203.42 / 6112.11 / 6108.31 / 6111.20） | 272 |
| `specStatus` / `dimStatus` | 字段状态。**注意：当前值「已复核 / 已核尺码表」是生成器写的占位状态，不代表版房真的核过** | 272 |

同一份数据落在三个地方，口径一致：

- `assets/data.js` —— 前端离线快照（`window.DB`）
- `data/db.json` —— 给 IT / BI 的 JSON（15 个顶层键：meta / stats / materials / brands / currency / products / codes / vehicles / axles / fitments / tests / customers / leads / scoreRules / templates）
- `data/xiaoman.db` —— SQLite（14 表 + 2 视图 + 8 索引，`node build\make-db.mjs` 从 `db.json` 生成），列名已经改成童装口径：`size_range`（尺码段）、`gsm`（克重）、`fit`（版型）、`brand_line`（品牌线）

```sql
-- 客户发来一个款号，问「这是什么款、什么码、多少钱」
SELECT * FROM v_style_profile WHERE code = 'DR2601001';

-- 某个款式系列覆盖哪些尺码段、对应哪些款号、置信度多少
SELECT series, size_band, code, fit_type, conf FROM v_size_band_fit
WHERE series LIKE '%云朵泡泡%';

-- 客户只给一个条码，先归一化再找款
SELECT p.code, p.name_zh, p.size_range FROM codes c
JOIN products p ON p.id = c.pid WHERE c.norm = '6972026112300';
```

> `db.json` 里的字段名仍沿用 `vehicles`（款式系列）、`axles`（尺码段）、`fitments`（适穿关系）、`holes`（克重）、`pos`（版型），只为兼容旧代码；SQLite 和界面已经全部换成童装说法。改文案前先看 `docs/术语映射.md`。

### 4.2 用户画像与关系网

目标不是「做个粉丝列表」，而是回答销售的两个问题：**谁值得花时间**、**谁能替我们说一句话**。

童装的买家画像很不一样：拍板的人往往是**妈妈**，决策依据是「好不好看 + 会不会过敏 + 码准不准」，而不是参数表。

数据模型（17 个演示账号，接平台 API 后可批量导入）：

| 字段 | 用途 |
|---|---|
| `type` | 母婴连锁 / 买手店 / 电商自营 / 进口商 / 批发商 / 宝妈 KOC / 采购经理 / 贸易商 |
| `followers` / `following` | 影响力与「他关注谁」 |
| `tags` | 常出镜的品类与尺码段，直接映射到可推款号 |
| `intent` | 意向度（0–100），决定跟进优先级 |
| `community` | 东南亚 / 中东 / 拉美 / 独联体 / 欧洲，用于分区运营 |
| `action` | 系统给出的下一步动作，不是空话 |

关系网用 SVG 画：节点大小 = 粉丝量，颜色 = 区域，外圈 = 高意向（≥85），橙色虚线 = 关注品牌号。点节点出画像卡：粉丝/关注/作品/互动率、画像标签、关系网名单、**常推品类 → 可推款号 → 报价**、推荐动作、一键生成该语种私信草稿。

三个立刻能用的判断：

1. **关键节点**：粉丝里同时出现多个区域账号的，是跨区影响者，优先寄样。
2. **终端 vs 中间商**：只发目录的贸易商（意向 34）不用陪聊；母婴连锁采购（意向 91）直接约视频看样。
3. **内容反哺**：谁经常拍「幼儿园穿搭」「演出服上身」，就给他对应系列和脚本，转化率最高。

### 4.3 聊天浮窗：后台听消息，命中款式就提醒

销售的真实场景是：WhatsApp、TikTok 私信、Facebook、Instagram 四个窗口同时闪，时差一乱就漏。

浮窗做三件事：

1. **聚合**：四个通道的消息进同一条流，标来源、标当地时间；
2. **识别**：每条消息过一遍匹配引擎（阿语、西语、葡语、印尼语、越南语都能识别款式、尺码、款号，靠的是别名表而不是翻译）；
3. **提醒**：命中就弹卡片 —— `客户问「演出 110」→ 云朵泡泡 DR2601001 · $13.56/件 · 90–140cm`，附「加入报价」「复制回复」；没命中就自动给「三步定码法」索要照片的话术（平铺同款 / 水洗标特写 / 身高对照门框）。

识别链路和选款页是同一条，所以口径不会打架。当前为**演示回放模式**（10 条多语种真实风格消息），接入方式见 §6。

### 4.4 获客内容引擎：泛流量做认知，垂直流量做转化

童装是**高关注、低专业度**的品类——纯硬广没人看，纯种草又带不来批发单。方案把内容分两条线：

| 流量类型 | 内容形态 | 目标 | 衡量 |
|---|---|---|---|
| 泛流量 | 「110 码买回去像 120」「孩子长得快，码表到底怎么选」「幼儿园演出服怎么不踩雷」这类反常识科普 | 让宝妈和店主记住 XIAOMAN KIDS | 完播率、评论里问尺码的数量 |
| 垂直流量 | 面料克重实测、起球对比、演出服上身、检测报告解读 | 让采购能直接下单 | 私信询盘数、资料包索取数 |

**热门视频雷达**：按语种/国家列出近 7 天高互动选题（12 条演示数据），每条标注「为什么火」的角度（码表差异、面料起球、演出季、亲子同款、换季清仓…）和可挂的款号。

**脚本生成器**：选款 + 市场 + 语种 + 平台 + 时长 + 痛点，输出

- 6 个分镜（0–3s 钩子 / 3–8s 冲突 / 8–16s 上身+细节 / 16–24s 质检背书 / 24–30s 场景 + CTA）
- 目标语种口播稿（ES / PT / AR / EN / ID / VI / TR）
- 话题标签、拍摄清单
- **一段可直接粘贴给任意大模型的提示词**（含款号参数、痛点、平台、时长、合规要求）

最后这项是关键：本机生成的是「结构正确的初稿」，真正的母语润色交给大模型或本地员工，避免编造认证、避免机翻腔。

## 5. 五分钟演示脚本

1. **痛点**：客户说「幼儿园演出，女孩，大概 105cm」→ 先用三步定码法翻成 110，再搜「云朵裙 110 300 件」→ 出候选款 + 尺码段表（100 / 110）+ 3 个消歧问题。
2. **报不上码的场景**：搜「110」→ 不急着给唯一款，先给尺码段说明（110 = 105–115cm、3–4 岁），再按品类收窄。
3. **客户只给编号**：搜「DR2601001」→ 96 分直接命中；搜条码「6972026112300」→ 98 分，附编号类型与来源。
4. **凑资料**：加入报价 → 300 件自动落到 0.88 档 → 报价单 → 资料包 → 打印预览 → 另存 PDF / 下载 ZIP。
5. **接线索**：工作台看到「现在该联系谁」，按当地时间排好；进询盘线索看评分依据。
6. **浮窗**：点右下「模拟新消息」→ 阿语询盘 → 1 秒内弹出「演出连衣裙 → DR2601001」。
7. **画像**：用户画像页点一个母婴连锁采购 → 意向 91 → 生成西语私信。
8. **内容**：获客内容页点「用此选题」→ 自动带出该市场语种和款号 → 生成脚本 → 复制 AI 提示词。

| 四期 | 90 天 | 内容排期与素材库；大模型 API 做母语脚本与自动回复草稿；按询盘-报价-成交做归因 | 获客可衡量 |

**集成方式**：`data/xiaoman.db` 是标准 SQLite（14 表 + 2 视图），BI 工具与 CRM 可直接读；要 JSON 的用 `data/db.json`，要批量回填的用 `data/导入模板.xlsx`。若要多用户再迁 MySQL/PostgreSQL，只改连接串（表结构按三范式设计，`alias` / `certs` / `traits` 等列为兼容旧系统保留 JSON 文本）。

**不建议做的事**（写在方案里，避免走弯路）：

- 不要试图一次把「所有系列 × 所有码段」补全——先补近 12 个月实际成交的 50 个款；
- 不要让销售自由编辑款号主数据——只能提「待复核」，否则编号体系三个月就烂；
- 不要用爬虫抓私信——违反平台条款，用官方 API 或人工转发；
- 不要把「按年龄推荐」当卖点——码表不一致，年龄只能初筛。

## 7. 边界与风险（必须如实告知）

1. **演示数据**：价格（$3.47–46.05/件）、MOQ（50–200 件）、交期、客户名、质检报告编号均为示例结构，不代表公司真实数据。交期文案目前仍有两套口径（浮窗「现货 3–7 天，改色 / 换面料 / 换标 15–25 天」，报价单页脚「定金后 25–35 天」），对外前必须统一。
2. **适穿置信度**：当前 44 条适穿关系中，**0 条「已确认」、20 条「高」、17 条「中」、7 条「低」**。低置信度不得直接对大货报价，界面已用颜色区分；不靠编号、只靠「系列 + 码段」的匹配分最高只到 86，就是这条限制的体现。
3. **质检报告**：12 份报告覆盖 12 个款，标准覆盖 GB 31701-2015（甲醛 / pH / 芳香胺 / 绳带 / 重金属）、GB 18401-2010（色牢度）、GB/T 4802.1（起球）、GB/T 8628（水洗尺寸变化率）、GB/T 3921（耐汗渍）、GB 5296.4（标识）、OEKO-TEX 100。**报告号与实验室名称是演示结构，不能当真实证书使用。**
4. **图片**：272 张款式图是 `build/make_kids_images.py` 按款号参数**程序绘制的款式示意**（900×1200），不是实拍，不能当验货依据；站内实拍图来自 **Burst（Shopify 免费商用图库，免署名）**，可商用，但不要二次转授权或标成自家拍摄。
5. **尺码表状态字段是占位值**：`specStatus` 全部为「已复核」、`dimStatus` 全部为「已核尺码表」，这是生成器写的状态，不代表版房逐款核过。真实尺码表（衣长 / 胸围 / 腰围 / 裤长）要版房出，补齐前不要用系统数据承诺「一定合身」。
6. **未成年人信息**：选码时客户会报孩子身高体重，这属于未成年人个人信息。方案里只用于当次选码，不写进客户档案、不导出、不进画像；聊天记录里的联系方式按内部资料管理，导出功能建议加登录与审计。
7. **认证表述**：对外只写实际持有的 GB 31701-2015（A/B 类）、GB 18401-2010、OEKO-TEX Standard 100、BSCI 验厂、GRS 再生涤纶（部分款）；脚本生成器内置「不夸大认证」的约束。

## 8. 附录

### 8.1 定价公式

```
单价 = 基准价 × 面料系数 × 数量阶梯 × 客户等级 × 价格等级
数量阶梯：1–99 件 → 1.00 ｜ 100–299 件 → 0.94 ｜ 300–999 件 → 0.88 ｜ ≥1000 件 → 0.82
客户等级：A → 0.97 ｜ B → 1.00 ｜ C → 1.03
价格等级：大客户 → 0.95 ｜ 标准 → 1.00 ｜ 经济 → 0.96
面料系数：精梳纯棉 1.00 ｜ 莫代尔 1.18 ｜ 摇粒绒 1.12 ｜ 涤纶防水布 1.35 ｜ 竹节棉 1.08 ｜ 羊毛混纺 1.55
```

运费为估算值（单箱 CBM × 件数 ÷ 40 × 120），正式报价以货代为准确认。MOQ 按款定（50 / 100 / 150 / 200 件），低于 MOQ 需在报价备注里写明加价或拒单。

### 8.2 线索评分

| 维度 | 权重 | 说明 |
|---|---|---|
| 基础分 | 30 | 有明确需求即得 |
| 终端属性 | +18 | 名称 / 备注含母婴连锁、童装店、买手店、门店 |
| 贸易商特征 | −14 | 名称含 Trading / Import & Export / FZE |
| 需求具体度 | +14 / +10 | 有明确款号 +14；只提到品类（连衣裙、卫衣…）+10 |
| 数量 | +12 | 出现件 / 套 / pcs / piezas + 数字 |
| 可触达性 | +10 | 有实名联系人，而不是只有公司名 |
| 时区可判 | +4 | 能算客户当地时间 |

≥75 A 优先跟进 ｜ 55–74 B 常规跟进 ｜ <55 C 暂缓投入（只发目录）。分数封顶 99。

> 数据库 `score_rules` 表里另有一套更细的 6 维权重（终端 / 需求具体度 / 数量与频次 / 可触达 / 款式匹配 / 市场价值），是给「评分可配置」留的结构；当前界面实际按上表计算，两边还没合并，改评分规则时别只看一处。

### 8.3 字段字典

`data/xiaoman.db` 共 14 张表：`meta` / `company` / `materials` / `brands` / `series`（款式系列）/ `size_bands`（尺码段）/ `products` / `codes` / `fitments`（适穿关系）/ `tests`（质检报告）/ `customers` / `leads` / `score_rules` / `templates`；另有 2 张视图 `v_style_profile`（款 + 面料 + 编号数 + 适穿数）、`v_size_band_fit`（系列 × 尺码段 × 款）。`db.json` 的顶层键仍是 `vehicles` / `axles` / `fitments`，SQLite 与界面已换成童装列名，字段映射见 `docs/术语映射.md`。
